# Aria v0.1.0 产品蓝图

本文档基于当前仓库中的真实前端页面、Controller API、Rust Agent 能力整理，目标不是描述“理想中的大而全平台”，而是收敛出一个可演示、可交付、可持续开发的 `v0.1.0` 方案。

## 1. 产品定位

Aria 不是单点 VPN 工具，而是一套面向多租户场景的 `SD-WAN 控制平台`。

产品的核心价值是：

- 让节点可以被安全接入并自动组网
- 让网络策略可以被集中定义、下发、执行和回显
- 让运维过程从“人工排查”升级为“监控发现 -> AI 辅助 -> 人工确认 -> 结果留痕”

补充约束：

- Aria 是强多租户产品
- 每个租户拥有自己的管理平面
- 每个 Agent 节点只能且必须属于一个租户
- 节点归属一旦建立，不允许跨租户漂移或复用

## 2. 当前代码中的真实能力

当前仓库已经具备以下基础：

- Controller:
  - 节点注册、同步、Enrollment Token 管理
  - JWT 登录、租户与用户管理
  - ACL、带宽与策略管理 API
  - Agent 命令队列与 gRPC 命令流骨架
  - 监控接口与 AI 工具调用入口
- Agent:
  - WireGuard 接口与 Peer 管理
  - eBPF ACL 与 QoS 执行
  - 周期 Sync
  - Unix Socket 本地命令
  - 远程命令流框架
- Frontend:
  - Dashboard
  - Nodes
  - Routing
  - Policies
  - Bandwidth Control
  - Tokens
  - Tenant Management
  - Monitoring
  - AI Assistant
  - Settings

因此，v0.1.0 不需要继续“发明页面”，而是要把现有能力收成一条清晰的产品主线。

## 3. v0.1.0 的核心目标

v0.1.0 只承诺三条闭环：

1. 接入闭环
   `init -> 注册 -> 获取身份/配置 -> Agent online`
2. 控制闭环
   `前端下发 -> Controller 校验/存储 -> Agent 执行 -> 前端回显`
3. 运维闭环
   `监控发现 -> AI 建议 -> 人工确认 -> 执行结果留痕`

只要这三条闭环跑通，产品就具备可演示和可交付价值。

## 4. 产品的五个核心领域

### 4.1 Identity

负责：

- 用户
- 租户
- Enrollment Token
- 节点身份
- 节点运行凭据

建议统一的核心对象：

- `User`
- `Tenant`
- `EnrollmentToken`
- `NodeIdentity`
- `NodeCredential`

凭据边界：

- `JWT`：用户登录态，只用于控制台与北向管理 API
- `EnrollmentToken`：节点首次注册使用，只用于 Agent 接入
- 两类 token 必须在接口、文档、前端命名中明确区分

### 4.2 Connectivity

负责：

- 节点接入
- 节点在线状态
- WireGuard peers
- 路由发布
- 站点互联

核心对象：

- `NodeRuntimeState`
- `PeerTopology`
- `AdvertisedRoute`

### 4.3 Policy

负责：

- ACL
- QoS / 带宽控制
- 路由策略
- 远程命令
- 策略版本

核心对象：

- `Policy`
- `DesiredStateVersion`
- `CommandExecution`

### 4.4 Operations

负责：

- 监控
- 告警
- 审计
- Agent 执行结果
- 状态回显

核心对象：

- `AppliedState`
- `ObservedState`
- `Alert`
- `AuditEvent`

### 4.5 Copilot

负责：

- AI 查询
- AI 建议
- 人工确认
- 工具执行
- 结果解释

核心对象：

- `Suggestion`
- `ActionPlan`
- `ApprovalRecord`

## 5. 统一的产品主流程

### 5.1 租户开通

1. 管理员登录
2. 创建或选择租户
3. 创建租户用户
4. 生成 Enrollment Token

### 5.2 节点接入

1. 在目标机器运行 `aria-agent init`
2. Agent 生成 WireGuard 密钥和 bootstrap 配置
3. Agent 首次向 Controller 注册
4. Controller 校验 Token、建立节点身份、分配 `node_id` 与 `assigned_ip`
5. Agent 保存运行状态并首次同步
6. 节点在控制台显示为 `online`

### 5.3 策略发布

1. 用户在前端创建 ACL / QoS / Route / Command
2. Controller 校验租户边界、目标节点与参数
3. Controller 生成新的 `desired state version`
4. Agent 拉取或接收命令并执行
5. Agent 回传执行状态、错误信息和应用版本
6. 前端展示“待下发 / 已应用 / 失败”

### 5.4 异常处理

1. Monitoring 发现节点离线、同步失败或策略失败
2. AI 读取节点、策略、监控上下文给出建议
3. 用户确认后执行变更或远程命令
4. 系统记录审计、执行结果和恢复信息

## 7. 后端 API 分层

当前仓库已经完成北向管理 API 的 `v2-only` 收敛，但南向仍保留“固定 HTTP 入口 + gRPC 运行期通道”的双层模型。后续工作重点不再是清理 `/v1`，而是继续收口页面、状态回显和运维闭环。

### 7.1 Northbound API

提供给前端和管理员，当前统一走：

`/api/v2/...`

建议包含：

- `/api/v2/auth/...`
- `/api/v2/tenants/...`
- `/api/v2/tenants/{tenant_id}/nodes/...`
- `/api/v2/tenants/{tenant_id}/monitoring/...`
- `/api/v2/tenants/{tenant_id}/ai/...`
- `/api/v2/tenants/{tenant_id}/agents/...`
- `/api/v2/settings/...`

### 7.2 Southbound API

提供给 Agent，当前采用两层：

- 固定 HTTP 入口：
  - `/api/v2/agents/register`
  - `/api/v2/agents/unregister`
  - `/api/v2/agents/network`
  - `/api/v2/agents/certificates/{issue,renew}`
- gRPC 运行期通道：
  - `Register`
  - `Sync`
  - `CommandStream`
  - `ReportMetrics`

### 7.3 兼容层

当前真正保留的兼容/固定入口很少：

- `ariactl` 仍通过 `/api/v2/agents/network` 管理路由
- `/api/version` 仍供前端读取版本

历史上的 `/api/v1/*` 与裸业务路径不再作为当前主模型的一部分。

## 8. 节点身份与接入架构

### 8.1 设计原则

- 不再把 `public_key` 同时当作节点主键、网络身份和运行鉴权身份
- 不再把“预置证书托管部署”和“自助接入”混成一条流程
- 注册和运行期鉴权分离

### 8.2 建议的统一模型

- `node_id`: 平台主身份
- `wireguard_public_key`: 网络身份
- `machine_id`: 设备身份
- `auth_method`: `mtls` 或 `runtime_token`

额外约束：

- `tenant_id` 是节点的强归属字段
- `node_id + tenant_id` 共同定义节点管理作用域
- `public_key` 可以轮换，但不得改变节点租户归属
- `hostname` 仅用于展示，不得作为跨租户复用依据

### 8.3 两种接入模式

#### Managed Mode

用于 Ansible / 预置证书部署：

- 证书、配置、密钥预先下发
- Agent 直接进入运行态

#### Self-Enroll Mode

用于产品化接入：

- 用户执行 `aria-agent init`
- Enrollment Token 完成首次注册
- Controller 发放 `node_id + assigned_ip + runtime credential`
- Agent 保存状态并上线

### 8.4 v0.1.0 推荐方案

先不把“自动证书签发”作为必需能力。优先支持：

- 传输层使用 server TLS
- 首次接入使用 Enrollment Token
- 运行期使用独立的运行凭据
- Managed Mode 继续兼容现有 mTLS/预置部署

## 9. 配置与状态的拆分

Agent 当前配置对象同时承载了静态配置和运行时状态。v0.1.0 应拆分为两类：

### 9.1 Bootstrap Config

由用户或部署提供：

- controller 地址
- region
- interface
- bootstrap token
- 证书路径或接入模式

### 9.2 Runtime State

由 Agent 自己维护：

- node_id
- assigned_ip
- address
- current credential
- last_applied_version
- last_sync_status

这样可以避免：

- 用户修改配置破坏运行状态
- 热更新逻辑混乱
- 首次注册和运行期逻辑耦合

## 10. 控制面模型

当前 `sync` 更像“现查现拼”，v0.1.0 应升级为更明确的控制模型。

建议至少引入：

- `DesiredState`
- `DesiredStateVersion`
- `AppliedState`
- `ObservedState`

最小可见字段：

- `desired_version`
- `applied_version`
- `last_error`
- `last_applied_at`
- `last_seen`

有了这套模型，前端才能真实显示：

- 待下发
- 已应用
- 应用失败
- 当前偏差

## 11. 策略模型

当前安全策略、ACL、带宽控制有重叠。v0.1.0 应收口为统一的 `Policy Center`。

建议统一的策略模型：

- `policy_id`
- `tenant_id`
- `scope`
- `target_nodes`
- `kind`
- `spec`
- `priority`
- `enabled`
- `version`
- `status`

其中：

- `kind = acl`
- `kind = qos`
- `kind = route`
- `kind = command`

这样前端可以保留不同标签页，但后端不再是几套平行概念。

## 12. Monitoring 与 AI 的定位

### 12.1 Monitoring

v0.1.0 监控不追求大而全，优先接控制闭环相关指标：

- 节点在线数
- 最近同步成功率
- Peer 数
- ACL 规则数
- QoS 规则数
- 命令执行失败数
- 节点离线与同步失败告警

### 12.2 AI Copilot

AI 在 v0.1.0 的定位不是自动改网，而是：

- 查询上下文
- 解释异常
- 生成建议
- 发起待确认动作
- 返回执行结果说明

也就是：

`建议 -> 确认 -> 执行 -> 留痕`

## 13. 当前代码中仍需收口的问题

下面这几项里，前 3 项已经基本修正完成，后 3 项仍是接下来的主要产品工作：

1. API 命名空间不统一
   已完成。北向业务 API 已统一到 `/api/v2/...`，`v1` 代码与调用路径已清理。
2. 节点身份与运行鉴权未分离
   已完成。`node_id`、`tenant_id`、Runtime Token 与运行期拦截器已经形成新的基线。
3. `Sync` 仍是即时拼装，未版本化
   已完成基础版本化。`desired/applied/observed`、`policy_deliveries` 与节点收敛状态已接入控制面。
4. 前端菜单与后端领域模型未对齐
   部分完成。导航结构和权限已经基本对齐，但 `Nodes`、`Monitoring`、`Policy Center` 仍未完全收成一个连续工作流。
5. ACL / Policies / Bandwidth 的概念重叠
   部分完成。后端统一读模型和交付状态已具备，但前端仍保留多个页面和部分重复心智模型。
6. Monitoring 与 AI 尚未与控制闭环完全打通
   仍然成立。当前具备监控、命令、AI chat/confirm 入口，但主动告警、IM 确认、执行结果回写仍未闭环。
7. Platform / Settings 中仍存在占位能力
   已基础收口。`backup` 已做成最小真实能力，支持 `create/list/download/delete/upload/restore`；其他系统设置项继续隐藏，不展示 placeholder。

#### P0：Platform 能力做真（Settings / Backup）

**现状**：`Settings` 已移除原有本地假保存动作，`backup` 已支持 create/list/download/delete/upload/restore；全局备份恢复已收口为 `super_admin` 专用，下载走鉴权 API 客户端。

**目标**：在当前最小备份链路的基础上继续增强恢复安全性，包括 dry-run、选择性恢复、二次确认和更完整的审计；做不到的设置项继续保持隐藏或只读。

#### P0：Nodes + Monitoring + Policy Center 收口

**现状**：后端已经具备 `desired/applied/observed`、`policy_deliveries`、最近命令和节点监控详情。Nodes 详情第一阶段已经收口为单节点运维工作台，能展示控制状态、命令生命周期、策略投递、活跃告警和证书状态，并能带上下文跳转到 Monitoring 与 Policy Center。

**目标**：继续把 `Nodes` 变成主工作台，让用户能在一次问题排查中连续看到节点状态、最近策略、命令和收敛情况。下一步重点是把告警处置、AI 建议和执行审计继续并入同一条操作链路。

#### P1：深度自动化 IM 联动

**现状**：飞书/钉钉与 AI 能力已经有入口，但仍以被动问答和手动回看为主。

**目标**：实现主动告警推送、卡片确认执行、执行结果回写与审计留痕。

#### P1：自动证书签发阶段 B

**现状**：证书签发服务和 `issue/renew` 接口已经接入，但生命周期还没有完整覆盖注册、续签、撤销与可观测性。

**目标**：补齐注册期自动签发、到期前续签、删除/禁用节点时的证书失效处理。

#### P2：完整自愈闭环

**现状**：当前仍以“AI 建议 -> 人工确认 -> 执行”为主。

**目标**：为低风险动作引入自动执行、熔断和回滚，高风险动作保留人工确认。

#### P3：复杂多集群编排

**现状**：单 Controller 管理所有节点已经能支撑当前产品阶段。

**目标**：在单集群产品化足够稳定后，再引入多区域独立 Controller 与联邦编排。

## 15. 实施顺序

推荐按以下顺序推进：

1. 清理 placeholder 与假能力，先让平台页真实可信
2. 收口 `Nodes`、`Monitoring`、`Policy Center`，形成统一运维工作台
3. 把 Monitoring 与 AI 接到 IM 主动告警和确认执行
4. 补齐证书生命周期，提升生产可部署性
5. 在前 4 项稳定后，再考虑完整自愈与多集群编排

## 16. v0.1.0 闭环终点与停止规则

v0.1.0 的目标不是把三条闭环做成平台终态，而是让每条主链路至少有一条真实、可验证、可审计的完整路径。总停止规则是：

- 有真实数据，不是假页面。
- 有成功路径，也有失败路径。
- 前端展示真实状态，不靠 HTTP 成功猜测执行成功。
- 后端有审计或事件记录。
- 能通过自动化测试或冒烟测试复现。
- 超出这条链路的高级能力全部延期。

### 接入闭环终点

```text
管理员生成 token
-> 复制完整 installer 命令
-> 安装 aria-agent + Controller CA + systemd unit
-> Agent 注册
-> Controller 创建 node + assigned_ip + runtime token
-> Agent 首次 Sync
-> 前端 30 秒内看到 online/degraded
-> 节点详情能看到 last_sync / desired / applied / error
-> 全流程有审计
```

终点标准：一台新机器从 0 接入后，控制台能判断它是真 `online` 还是 `degraded`，并能解释原因。

2026-06-25 状态：Nodes 已提供接入向导，可创建 Enrollment Token、读取 Controller bootstrap contract 并生成完整 installer 命令；Controller 可提供 Agent 下载和 gRPC CA；Agent `init/up/doctor` 已能明确提示 CA、TLS server name、interface、配置和 systemd 常见问题；节点列表和详情已展示 `registered/syncing/online/degraded` 接入阶段与 next action。剩余验收是线上新机器从 0 执行接入冒烟。

### 控制闭环终点

```text
前端创建/更新/删除 ACL、QoS 或 Route
-> Controller 校验并写 desired_state_version
-> 生成 command_id / policy_delivery
-> Agent 执行
-> 回写 applied_state_version 或 failed reason
-> Policy Center / Nodes / Monitoring 看到同一个结果
```

终点标准：HTTP 成功不再等于执行成功；用户能看到每次策略是否真的被 Agent 应用。

2026-06-25 状态：ACL/QoS/Route 的 desired、command、delivery、applied/failed 回显已接入；剩余验收是线上真实 Agent 的策略创建、更新、删除和失败状态一致性冒烟。

### 运维闭环终点

```text
Monitoring 发现 sync_failed / policy_failed / node_offline
-> 生成 active alert
-> 用户点进 alert 看到证据
-> Ask AI 生成解释和建议
-> 用户确认 sync 或 health_check
-> Controller 执行命令
-> Agent 回写结果
-> alert / event / audit / node detail 都能看到处理结果
```

终点标准：用户能从一个告警出发，完成一次“诊断 -> 确认 -> 执行 -> 留痕”，并且失败也可见。第一阶段优先用 `sync_failed` 跑通样板链路，IM 卡片确认和无人值守自愈延期。

2026-06-25 状态：Monitoring 和 Node Detail 已打通 alert 上下文、Ask AI 预填诊断、Run Sync/Health Check、Resolve Alert；剩余验收是线上用 active alert 完整复现一次处置链路。

## 17. 最终确认

v0.1.0 的目标不是“功能最多”，而是“第一次把接入、控制、运维三条产品主链路跑通”。

确认后的最终方案是：

- 前端继续按工作流组织，并优先强化 `Nodes` 这个主工作台
- 后端维持按领域与南北向 API 分层
- 节点使用统一身份模型，不再仅依赖 `public_key`
- Policy 统一读模型继续收口，但不必强行砍掉各子域写接口
- Monitoring 与 AI 服务于控制闭环，而不是独立展示能力
- Platform 页面只保留真实可交付能力，不再展示 placeholder

该方案将作为后续代码重构与功能收敛的基线。
