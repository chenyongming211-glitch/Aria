# Onboarding Installer Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn node onboarding from a manual operator-assisted process into a repeatable control-console flow that produces a reliable install command, installs the Agent, installs Controller CA material, initializes runtime state, starts systemd, and shows online/degraded status with an actionable reason.

**Architecture:** Keep the Controller as the source of bootstrap facts: public Controller URL, gRPC endpoint, TLS server name, CA material, Agent artifact location, and default runtime options. The frontend renders a guided onboarding command from that contract. The Rust Agent stays responsible for local validation, state creation, service startup expectations, and clear failure messages.

**Tech Stack:** Go Controller HTTP API, Vue 3 + Element Plus frontend, Rust Agent CLI, systemd on Linux Agent hosts, shell installer generated by the frontend, GitHub Actions for Rust Agent/eBPF validation, low-bandwidth local deployment for Controller/frontend-only batches.

---

## Scope

This plan closes the first-stage onboarding installer gap only.

In scope:

- A public Controller bootstrap contract for install/onboarding facts.
- A frontend onboarding wizard that produces a complete install-and-init command, not only `aria-agent init`.
- A Linux installer script path that handles binary placement, CA installation, config/state directories, systemd unit creation, init, service start, and status checks.
- Agent-side validation and error messages for CA, TLS server name, interface, token, endpoint, and service startup mistakes.
- Onboarding progress visibility in Nodes: token created, token used, node registered, first sync, online/degraded, last error.
- Documentation and gray validation for one clean VM.

Out of scope:

- Full Agent auto-upgrade orchestration.
- Multi-Controller bootstrap selection.
- Complete certificate lifecycle automation beyond installing the Controller CA for gRPC TLS.
- QoS/ACL data-plane changes.
- AI-assisted operations flow.
- Unattended healing of broken hosts.

## Current Baseline

Current implementation already has these pieces:

- `frontend/src/views/Nodes.vue` has an onboarding dialog that can create an enrollment token and generate an `aria-agent init` command.
- `internal/api/v2/platform.go` exposes `GET /api/v2/controller-info` with version, capability, and gRPC TLS facts.
- `agent-rust/agent/src/main.rs` has `init` and `up` commands.
- `agent-rust/agent/src/config.rs` has default bootstrap and state paths: `/etc/aria/agent.yaml` and `/var/lib/aria/agent-state.yaml`.
- Online validation showed that manual binary upload plus manual CA installation can onboard a new node successfully.

The product gap is that a customer still needs operator knowledge to install the binary, place CA files, create systemd, pass the right CLI flags, and diagnose failures.

## Target User Flow

```text
Admin opens Nodes -> Add Node
-> creates enrollment token
-> reviews generated Linux install command
-> copies command to a fresh VM
-> VM installs aria-agent and Controller CA
-> command runs aria-agent init with token, CA, TLS, region, interface, public endpoint
-> systemd service starts
-> Agent registers and completes first sync
-> Nodes page shows registered -> syncing -> online or degraded
-> Node detail shows last sync, desired/applied, command stream, certificate, and last onboarding error if any
```

The expected first release target is Ubuntu/Debian amd64 with systemd. Other Linux families can use the same API contract later, but should not block this phase.

## API Contract

Add or extend a public unauthenticated bootstrap endpoint. Prefer extending the existing endpoint instead of creating parallel discovery endpoints.

Endpoint:

```http
GET /api/v2/controller-info
```

Required response fields:

```json
{
  "version": "0.2.48",
  "controller_api_url": "https://aria.yun",
  "grpc": {
    "server": "https://aria.yun:50051"
  },
  "grpc_tls": {
    "mode": "server",
    "ca_required": true,
    "server_name": "aria.yun",
    "ca_cert_path": "/etc/aria/certs/ca.crt",
    "ca_cert_url": "https://aria.yun/api/v2/controller-info/grpc-ca.crt",
    "ca_cert_sha256": "hex-encoded-sha256"
  },
  "agent": {
    "supported_os": ["linux"],
    "supported_arch": ["amd64"],
    "default_interface": "aria0",
    "default_region": "default",
    "install_dir": "/usr/local/bin",
    "config_path": "/etc/aria/agent.yaml",
    "state_path": "/var/lib/aria/agent-state.yaml",
    "systemd_unit": "aria-agent.service",
    "download_url": "https://aria.yun/api/v2/downloads/aria-agent/linux/amd64",
    "sha256": "hex-encoded-sha256"
  }
}
```

Add a CA download endpoint:

```http
GET /api/v2/controller-info/grpc-ca.crt
```

Expected behavior:

- Public endpoint, no JWT.
- Returns PEM bytes for the gRPC Controller CA.
- Returns `404` when gRPC TLS is disabled or no CA is configured.
- Sets `Content-Type: application/x-pem-file`.
- Does not return private keys.

Add an Agent binary download endpoint only if artifacts are available on the Controller host:

```http
GET /api/v2/downloads/aria-agent/linux/amd64
```

Expected behavior:

- Public endpoint only for the current release artifact.
- Returns `404` if the artifact is missing.
- Sets `Content-Type: application/octet-stream`.
- Sets a checksum header:

```http
X-Aria-Artifact-SHA256: <sha256>
```

If the Controller host should not serve binaries yet, keep `download_url` empty and have the frontend generate a command that expects the user to download/upload `aria-agent` separately. The first product-grade target should serve the binary to remove manual upload.

## Installer Command Shape

The frontend should generate a single command that pipes a versioned installer script from Controller and passes parameters explicitly:

```bash
curl -fsSL https://aria.yun/api/v2/install/agent.sh | sudo bash -s -- \
  --controller-api-url https://aria.yun \
  --server https://aria.yun:50051 \
  --token tk_xxx \
  --ca-url https://aria.yun/api/v2/controller-info/grpc-ca.crt \
  --ca-sha256 <sha256> \
  --tls-server-name aria.yun \
  --region tencent-cloud \
  --interface aria0 \
  --hostname "$(hostname)" \
  --public-ip auto \
  --public-endpoint auto
```

Installer behavior:

1. Require root or sudo.
2. Detect OS and architecture.
3. Install directories:
   - `/etc/aria`
   - `/etc/aria/certs`
   - `/var/lib/aria`
   - `/var/log/aria`
4. Download `aria-agent` to `/usr/local/bin/aria-agent`.
5. Verify binary SHA256 when Controller provides one.
6. Download CA to `/etc/aria/certs/ca.crt`.
7. Verify CA SHA256 when Controller provides one.
8. Write `/etc/systemd/system/aria-agent.service`.
9. Run `aria-agent init` with the exact arguments from the wizard.
10. Run `systemctl daemon-reload`.
11. Run `systemctl enable --now aria-agent`.
12. Print:
    - `systemctl status aria-agent --no-pager`
    - `journalctl -u aria-agent -n 80 --no-pager`
    - next UI step: refresh Nodes and open node detail.

Systemd unit content:

```ini
[Unit]
Description=Aria SD-WAN Agent
Documentation=https://github.com/chenyongming211-glitch/Aria
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/aria-agent up --interface aria0 --config /etc/aria/agent.yaml
Restart=always
RestartSec=5
LimitMEMLOCK=infinity
AmbientCapabilities=CAP_NET_ADMIN CAP_BPF CAP_PERFMON CAP_SYS_RESOURCE
CapabilityBoundingSet=CAP_NET_ADMIN CAP_BPF CAP_PERFMON CAP_SYS_RESOURCE
NoNewPrivileges=false
ExecStopPost=/bin/bash -c 'for i in {0..3}; do ip link del aria$i 2>/dev/null || true; done'

[Install]
WantedBy=multi-user.target
```

The interface in `ExecStart` must be generated from the wizard value. The default is `aria0`.

## Acceptance Criteria

The branch is complete only when all items are true:

- A user can open Nodes -> Add Node and create a token.
- The generated command installs `aria-agent` on a clean Ubuntu/Debian amd64 VM.
- The generated command installs Controller CA and uses `--tls-server-name`.
- The generated command writes systemd and starts `aria-agent`.
- The new node appears in Nodes within 30 seconds as `online` or `degraded`.
- Node detail explains last sync, desired/applied state, command stream, certificate status, and onboarding error if present.
- Missing CA, bad CA checksum, expired token, exhausted token, missing binary, and service start failure all produce clear messages.
- Agent restart does not consume the enrollment token again.
- Controller restart does not break Agent sync or command stream recovery.
- Branch GitHub Actions pass.
- Gray validation on a fresh VM passes.
- Version is bumped before deployment.

## Risk Controls

- Keep installer script public but parameterized; it must not embed token values server-side.
- Never expose private key material through controller-info.
- Return CA PEM only, not server certificate private key.
- Keep Agent binary download limited to the exact artifact path configured for the current release.
- Do not make `curl | bash` the only supported path; keep init-only fallback for users who preinstall Agent through Ansible or images.
- Do not auto-delete existing `/etc/aria/agent.yaml` or `/var/lib/aria/agent-state.yaml`. If they exist, installer must stop and print a re-run flag recommendation.
